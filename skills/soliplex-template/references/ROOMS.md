# Rooms: adding one, or provisioning one for a requester

Loads when: Load this reference to add a room to an existing stack from a bundled template, or to create a private RAG room on a requester's behalf under src/rooms-provisioned.

## Adding a room to an existing stack

To add a room to a stack — one generated by this skill, or any hand-built
Soliplex installation laid out the same way — render one of the skill's bundled
room templates with `scripts/add_room.py`. It is pure filesystem work (no Docker,
no running backend): it writes
`backend/environment/rooms/<room-id>/room_config.yaml` and makes sure
`room_paths` loads it. Generated stacks point `room_paths` at `./rooms`, which
auto-discovers every room beneath it, so no `installation.yaml` edit is needed
(reported as `covered`); installations that instead enumerate their rooms get
`- "./rooms/<room-id>"` spliced in (line-based, so comments and layout are
preserved). The `--reload=config` backend restarts on edits to existing
config files, but does **not** reload a newly created room: fire the
rooms-reload endpoint (soliplex#1475) after `add`, below.

1. **Show the bundled templates** and let the user choose one:

   ```bash
   uv run scripts/add_room.py list
   ```

   The templates are `chat` (conversational RAG), `search` (search-and-answer
   with citations), `minimal` (bare agent + prompt), and `sandbox` (file upload +
   bubblewrap code execution + RAG). Each renders with commented-out examples for
   adding custom tools and skills (both filesystem and entrypoint), for the
   operator to uncomment later. Pass `--project-dir` to list only the templates
   that stack can use: `sandbox` needs a stack generated with
   `enable_sandbox: true` (or with the backend's `security_opt` block
   uncommented), and `add` refuses it otherwise.

2. **Gather the parameters** with `AskUserQuestion`: `--room-id` (required;
   letters/digits/`.`/`_`/`-`, no leading dot — also the directory name and the
   `room_paths` entry), `--name`, `--description`, `--agent-template` (an agent
   `template_id` from `installation.yaml`, default `default_chat`; the other
   shipped templates are `alternate_chat` and `title`), a system prompt
   (`--system-prompt "…"` inline, or `--prompt-file PATH` to drop a `prompt.txt`
   in the room and reference it; omit both to take the template's default), and
   `--rag-stem` for the chat/search/sandbox templates (the LanceDB stem the room
   reads, default `haiku.rag` — set it to a database created with `rag_db.py`).

3. **Dry-run first**, then apply (run from the stack dir, or pass
   `--project-dir`):

   ```bash
   uv run scripts/add_room.py add --project-dir /path/to/stack \
       --template chat --room-id handbook \
       --name "Handbook" --description "Q&A over the staff handbook" --dry-run
   ```

   Drop `--dry-run` to write. The room directory must not already exist (pass
   `--force` to overwrite it). The `room_paths` line reports `added`, `covered`
   (a `./rooms` entry already loads it), or `unchanged` (already listed).

4. **Fire the rooms-reload endpoint** so the running backend picks up the
   new room (a backend on soliplex < 0.87 lacks the endpoint; on those,
   restart the backend instead):

   ```bash
   curl -s -XPOST http://localhost:<nginx_http>/api/v1/installation/reload/rooms
   ```

5. **Verify** the install now loads the room:

   ```bash
   uv run scripts/soliplex_config.py rooms --project-dir /path/to/stack
   ```

   Then point the user at the generated `room_config.yaml` to uncomment the
   tool/skill examples or refine the prompt.

## Provisioning a room for a requester

To create a private RAG room *on behalf of a user* — its own database fed
from the room's uploads, access for that user alone, the config committed
to the stack's `src/rooms-provisioned` repository — run
`scripts/provision_room.py`. Unlike `add_room.py`, it needs the stack up:
it runs the provisioner in a one-off `soliplex-dev` container (built on
first use), which reloads the ingester and the backend. The stack's
`docs/operations/room-provisioning/` pages describe every step and setting.

1. **Gather** the requester (`--username`, plus `--email` and
   `--display-name` when known; or their claims as JSON with `--claims`)
   and the room's `--name`, optionally `--description` and `--slug`. The
   room id is `<username>:<slug>`; the slug defaults to one derived from the
   name (`"Q3 Plans"` → `q3-plans`).

2. **Run** it from the stack dir, or pass `--project-dir`:

   ```bash
   uv run scripts/provision_room.py --project-dir /path/to/stack \
       --username alice --email alice@example.com \
       --display-name "Alice Example" --name "Q3 Plans"
   ```

   The provisioner authenticates with service tokens it mints for itself
   (subject `soliplex-provisioner`). The backend admits them through an
   `admin_users` entry, which `stack-init` adds; the provisioner checks
   before changing anything, and names the entry when it is missing. Then
   offer to run `docker compose run --rm --quiet-build stack-init`, which
   adds it; ask the user rather than running it yourself.

3. **Read the outcome**: exit `0` means the room is live; `1` means the room
   is committed but a later step failed — relay each printed "still to do"
   line; `2` is an error, and nothing was left behind (a failure part-way is
   rolled back). A taken id, or a name that yields no slug, is an error:
   ask the user for another name or an explicit `--slug`. So is an id whose
   database, ingester entries, uploads or authz policy already exist (left
   from a room removed by hand): the error names each one. Report them to
   the user, who decides whether to remove them; never delete them
   yourself to get past the refusal.
